# Из спеки в задачи

Спека описывает желаемое поведение, раздел **«Расхождения с кодом»** — где
реальность с ним не сходится. Каждая строка там помечена как кандидат в
задачу. Этот скилл превращает кандидатов в задачи на доске.

Почему не `speckit-tasks` + `speckit-taskstoissues`: они работают с
`tasks.md`, заводят issues с заголовками вида `T001: …` без лейблов, доски и
статусов, и оставляют `tasks.md` вторым трекером — что запрещено корневым
`CLAUDE.md`. Здесь источник другой: не план новой фичи, а разница между
спекой и кодом.

## 1. Собрать материал

```bash
node .claude/skills/spec-to-issues/scan-gaps.js [specs/05-news/spec.md] [--check]
```

Без пути просматривает все спеки. `--check` спрашивает GitHub, упоминаются ли
коды требований в существующих issues — то, что уже покрыто, заводить второй
раз не нужно.

Скрипт определяет роль по слою кода: `-Б-` → backend, `-Ф-` → frontend, оба →
парные задачи. Слой `-О-` роли не задаёт: продуктовое правило может чиниться
где угодно, решай по смыслу расхождения.

## 2. Сгруппировать

**Одно расхождение ≠ одна задача.** Это главное решение скилла, и оно
смысловое, а не механическое:

- **Несколько строк — одна задача**, если чинятся одной правкой в одном месте.
  Пример: `ЗАК-Ф-12`…`ЗАК-Ф-15` (режим подложки) и `ЗАК-Ф-18` (битая картинка)
  — всё это поведение изображения в карточке, одна задача.
- **Одна строка — две задачи**, если нужен и сервер, и клиент. Пример:
  `ЗАК-Ф-16`, `АДП-Б-01` — сервер отдаёт размерные варианты, клиент выбирает
  по месту. Это парные задачи в разных репозиториях со ссылками друг на друга.
- **Отдельная задача**, если правка независима и её можно взять сразу.

Ориентир по размеру: задача — это то, что один исполнитель доводит до PR за
один заход. Если в acceptance criteria больше десятка пунктов о разном —
скорее всего, задач две.

## 3. Определить порядок

Расставить зависимости **до** создания issues — иначе исполнитель возьмёт
заблокированную задачу и упрётся:

- парная задача на фронте блокируется серверной: принимать новый контракт
  пока некому;
- задача, меняющая геометрию или контракт, идёт раньше тех, кто на неё
  опирается;
- починка того, что уже врёт пользователю, идёт раньше улучшений.

## 4. Завести issues

Тело — по шаблону корневого `CLAUDE.md`:

```markdown
## Описание
Что не так сейчас и чем это грозит. Ссылка на требования спеки по кодам
и на саму спеку. Внятно объяснить последствие, а не пересказать требование.

## Acceptance Criteria
- [ ] Проверяемые пункты со ссылками на коды требований
- [ ] Обновлён `PROJECT_MAP.md`   ← если создаётся что-то новое

## Зависимости
Что блокирует эту задачу и что блокирует она. Кросс-репо — полным путём
`MACTEPwar/streamer.API#N`, иначе GitHub не свяжет ссылку.

## Не входит
Что сознательно осталось за границами, чтобы не размывать задачу.
```

Заголовок — в стиле Conventional Commits, как принято в проекте:
`fix: витрина отдаёт содержимое карточек`, `feat: размерные варианты
изображений`. Не `T001: …`.

```bash
gh issue create --repo MACTEPwar/streamer.API --label backend \
  --title "…" --body-file <файл>
```

**Сначала серверные, потом клиентские** — номера backend-задач нужны, чтобы
подставить их в раздел «Зависимости» парных фронтовых. В блокирующие задачи
добавить обратную ссылку комментарием.

## 5. Поставить на доску

Issue не попадает на доску сама, а добавленная карточка приходит **без
статуса** и не показывается ни в одной колонке. Команды и идентификаторы — в
[.claude/board.md](../../board.md).

- **«К выполнению»** — задачам, которые можно брать прямо сейчас;
- **«Бэклог»** — тем, что ждут зависимости.

Это различие и делает доску полезной: исполнитель видит, что свободно, а не
перебирает всё подряд.

## Проверить себя

- Каждая непокрытая строка расхождений попала хотя бы в одну задачу
  (`scan-gaps.js --check` после создания должен показать «без задачи: 0»).
- У каждой парной задачи ссылки в обе стороны.
- Ни одна задача не осталась без статуса на доске.
- Заголовки не дублируют друг друга и говорят, что чинится, а не какой код
  требования затронут.
